15/35 min

One field, two ways

With the plugin
the_field( 'subtitle' );
With core
register_post_meta( 'post', 'subtitle', [
  'type'         => 'string',
  'single'       => true,
  'show_in_rest' => true,
] );

Four more lines, and the value now has a type, a schema and a REST route. The theme stops being the only thing that knows the field exists.

Binding it to a core block

The old way
acf_register_block_type( [
  'name'            => 'subtitle',
  'render_template' => 'blocks/subtitle.php',
] );
The binding
<!-- wp:paragraph {
  "metadata": { "bindings": {
    "content": {
      "source": "core/post-meta",
      "args": { "key": "subtitle" }
    } } } } -->

No custom block, no render template, no plugin. A core paragraph that reads your meta, and an editor who can still style it like any other paragraph.

What just happened

  • —The block is core, so it keeps every feature core adds to it later.
  • —The value is meta, so the REST API and wp-cli already understand it.
  • —The binding is markup, so it lives in the pattern, not in a PHP file.
  • —Nothing here is yours to maintain.

When you do need one

block.json
{
  "apiVersion": 3,
  "name": "dude/timeline",
  "title": "Timeline",
  "render": "file:./render.php",
  "attributes": {
    "year": { "type": "string" }
  }
}
render.php
<div <?php echo get_block_wrapper_attributes(); ?>>
  <?php echo esc_html( $attributes['year'] ); ?>
  <?php echo $content; ?>
</div>

One JSON file and one PHP file. No build step, no React, no node_modules. This is the block you write when the shape genuinely does not exist yet.

Moving the data

  • —ACF stores the value in postmeta under the field name. That part is easy.
  • —It also stores a companion key prefixed with an underscore. Drop it.
  • —Repeaters are stored as a count plus indexed keys. That part is not easy.
  • —wp-cli, a dry run, and a staging copy. Never in place, never on a Friday.
